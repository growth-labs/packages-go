# Shared capabilities — the estate index

Generated by fulcrum-labs/platform-foundations from the catalogs each home maintains; do not edit here. Before adding a mechanism, read this repo's `docs/agent/mechanisms.md`, then find the package, service or capability below that already serves the need and extend it. The doctrine, the homes and the `Reuse:` declaration are in `.claude/rules/shared-capabilities.md`.

## Where new behaviour lives

| Class of work | Home |
|---|---|
| Automated, scheduled, cross-site or media work; anything that should inherit the scheduler, receipts and monitoring | Go plane: a `fulcrum-labs/foundry` capability (host record + package + migrations + receipts + tripwire) |
| Behaviour shared by Workers-runtime sites and apps | `@growth-labs/<pkg>` in `growth-labs/packages` |
| Behaviour shared by Go services | `growth-labs/packages-go/<module>`; extract at the second real use, never copy |
| Identity, sessions, sign-in | identity-platform (OpenAuth issuer) through `@growth-labs/auth` or `packages-go/auth`; never a standalone auth path |
| Email | Workers: `@growth-labs/email` (transactional) and `@growth-labs/mailer` (campaigns); Go: `packages-go/email` (Fastmail JMAP) |
| UI | Astro sites: StarwindUI Pro (`components/starwind/`); React/SPA apps: the Growth Labs tokens (see the estate index for the current package state) |
| Domain logic only this app has | this app, until a second consumer appears; then extract |

**Stability:** `stable`
**Summary:** OpenAuth client integration for Astro sites, with an explicit-config @growth-labs/auth/workers surface for Cloudflare Workers and Hono.

**Use when**
- The site needs JWT verification, session cookies, or gated routes backed by the shared issuer.
- A Cloudflare Worker or Hono app needs explicit-config OpenAuth relying-party routes without Astro or Analytics.

**Do not use when**

- For confidential Astro clients, configure clientSecret with a Worker secret or Secrets Store binding name

### `@growth-labs/conformance`

**Stability:** `experimental`
**Summary:** Reusable fleet publication conformance harness with cache-safety primitives, privacy-safe body-leak receipts, shared response headers, and exact-source Astro hash CSP policy.

**Use when**
- A site or CI job needs machine-parseable publication conformance evidence.
- You need to verify security headers, cache semantics, metadata, JSON-LD, images, publication surfaces, Discover eligibility, or build evidence from fixtures.
- You want the shared SSR/static header and cache policy helpers without creating a central fleet runtime.

**Do not use when**
- You need a hosted central monitor or scheduler; use site-owned CI or monitoring jobs to consume this package.
- You need to mutate production/customer surfaces; this package is evidence-only.

**Minimal setup**
- Install @growth-labs/conformance
- Create site-owned fixtures with captured response headers, HTML, publication surfaces, cache variants, security receipts, and build evidence
- Run runSiteConformance for each site fixture or runFleetConformance for a fixture array
- Parse SiteEvidenceBundle or FleetEvidenceBundle with the exported schemas
- Use buildSharedPublicationHeaders when adopting the package-owned SSR/static header policy
- Use buildAstroCspConfig as security.csp and disable the shared fallback CSP when Astro owns route hashes
- Use the cache-safety subpath to validate gateway/inner policy and controlled request-state sentinels

**Working example:** `packages/conformance/README.md`

**Common mistakes**
- Treating the package as a central fleet runtime instead of a reusable per-site harness.
- Marking publication surfaces NA without both capabilityBoundary and evidence.
- Treating enforced CSP as passing without consumer-supplied functional-probe and CSP-report receipts.
- Combining Astro's route-specific hash CSP with a second generic CSP header that blocks the generated hashes.
- Passing an inline-style inventory without astroMajorVersion: 7. Astro 6 cannot represent attribute-scoped style resources and the helper fails closed by default.
- Adding HSTS includeSubDomains/preload before host inventory proof.
- Letting crawler and public variants share cache keys when their response content or headers can differ.
- Testing fixtures by grepping source instead of running runSiteConformance and asserting finding codes.
- Including raw sentinel values in live conformance evidence.

### `@growth-labs/ezoic`

**Stability:** `experimental`
**Summary:** Server-side Ezoic ad-mount integration with an Astro-hashed strict-dynamic loader bootstrap, runtime-safe entitlement suppression and consent-awareness for Astro + Cloudflare sites.

**Use when**
- The site monetizes with Ezoic and needs server-rendered ad slot placeholders.
- You want Insider/entitlement suppression or consent-gated ad rendering out of the box.

**Do not use when**
- You have not provisioned an Ezoic account or site ID — siteId is operator-gated.
- The site uses a different ad provider.

**Minimal setup**
- Install @growth-labs/ezoic
- Add ezoic({ siteId, injectLoader: true, adsTxt, accessCheckModule }) to integrations in astro.config.mjs after auth and consent
- Enable the advertising CSP profile: script-src needs strict-dynamic; img-src/frame-src/connect-src need https: for ad creatives, safeframes and bid traffic
- Use <EzoicAd slotId={NNN} /> in page layouts where ad slots should render

**Required env**
- `EZOIC_SITE_ID`

**Working example:** `packages/ezoic/CHANGELOG.md`

**Common mistakes**
- Forgetting to add ezoic after auth and consent in astro.config.mjs — the middleware reads locals.user set by auth.
- Hardcoding siteId in source — it is an operator secret; inject it from the environment.
- Deploying under a strict exact-origin CSP. Ezoic cannot run under one: the demand-partner origins are open-ended and Ezoic publishes no domain list. Ads then fail SILENTLY — empty placeholder divs, no console error. script-src needs strict-dynamic, and it does not extend to img-src/frame-src/connect-src.
- Adding https://www.ezojs.com as a script-src trust root under strict-dynamic. CSP3 ignores host sources in that policy; install a release with the Astro-hashed bootstrap instead.
- Using the deprecated isInsider callback. It is captured at build time and lost before middleware runs on Workers, so it does nothing in production. Use accessCheckModule.
- Passing a non-numeric slotId. The dispatcher parses the trailing integer off the element id, so a string id is silently dropped.

### `@growth-labs/mcp-auth`

**Stability:** `stable`
**Summary:** Authentication and identity layer for MCP services. Resolves an inbound HTTP request into a typed Actor and supplies a swappable resolver chain: tokenMapResolver for static service tokens and oauthJwtResolver for human-user OAuth access tokens.

**Use when**
- Building an MCP service Worker that needs bearer-token or OAuth authentication.
- You need a typed Actor object passed through middleware for authorization and audit.

**Do not use when**
- The service is not an MCP service (use @growth-labs/auth for sites running OpenAuth client flows).
- You need session management, registration, or password-reset flows — those are identity-platform concerns.

**Minimal setup**
- Install @growth-labs/mcp-auth

- Build tokenMapResolver({ envVarName }) against your realm-specific token-map env var for service tokens
- Compose mcpAuthMiddleware({ resolvers: [oauth, tokens], audit }) and apply requireRole / requireAnyRole per-tool
- Implement the AuditWriter interface against your realm's audit storage (D1, Logpush, Tail Worker)

**Working example:** `packages/mcp-auth/README.md`

- Treating the package as an OAuth issuer; this package only verifies access tokens against an externally-injected issuer URL and audience — issuance lives in identity-platform.
- Advertising an OAuth scope without setting requiredScopes; the resolver enforces scopes only when the consumer explicitly configures them.

### `@growth-labs/mcp-server`

**Stability:** `stable`
**Summary:** Server framework for MCP services. Wraps a transport-agnostic JSON-RPC dispatcher with conventions every MCP service needs: defineMcpTool primitive, createMcpServer composition, audit/metrics interfaces, role-based authz, validation, rate limiting, and OAuth protected-resource metadata discovery.

**Use when**
- Building an MCP service Worker that needs more than a hand-rolled protocol implementation.
- You want consistent audit / metrics / error envelopes across multiple MCP services.
- Your tools need role-based authorization, input/output validation, or rate limiting wired by the framework.

**Do not use when**
- The service is not an MCP service.
- You need MCP resources (distinct from tools); v1 only supports tools.

**Minimal setup**
- Install @growth-labs/mcp-server and @growth-labs/mcp-auth
- Define each tool with defineMcpTool({ name, description, input_schema, output_schema, examples, stability, required_roles, handler })
- Compose with createMcpServer({ service, version, auth, audit, metrics, tools, protectedResourceMetadata }) and export the returned fetch from your Worker
- Implement the AuditLogger and MetricsEmitter interfaces against your realm's storage

**Working example:** `packages/mcp-server/README.md`

**Common mistakes**
- Constructing tool definitions as plain objects instead of through defineMcpTool — createMcpServer rejects these at registration.
- Storing internal error details in McpError.message — that field is returned to clients. Put internals in McpError.internal.
- Setting outputValidationMode to 'strict' in production — slight handler drift will throw and break clients. Use 'strict' only in dev/CI.
- Omitting protectedResourceMetadata on an OAuth-capable MCP service — clients cannot discover the authorization server and may guess the wrong /authorize URL.
- Trying to swap @modelcontextprotocol/server in directly — wait for it to graduate from alpha; the Transport abstraction makes the switch trivial when it does.

**Related packages**
- `mcp-auth`

### `@growth-labs/mcp-wrapper-scaffold`

**Stability:** `experimental`
**Summary:** Scaffold for fulcrum read-only MCP wrapper Workers. Provides createWrapperServer with method+path allowlist enforcement, dual-accept auth via verifyAgentAuth (legacy shared bearer against a Secrets Store binding OR short-lived EdDSA gateway JWTs with pinned alg/iss/aud, required kid, dual-key rotation), verifyAgentToken (legacy exact-compare, unchanged), and getGoogleAccessToken (RS256 SA JWT exchange). Per-tool-call metrics include auth_source (shared-bearer | gateway-jwt) — the shared-bearer retirement-gate signal. The wrapper allowlist is the only path to upstream APIs — gatedFetch is NOT exported; wrappers reach the network via ctx.fetch (closure pre-bound to the allowlist) passed to each tool handler.

**Use when**
- Building a read-only Cloudflare Worker that wraps a third-party HTTP API and exposes it as MCP tools (e.g. GA4, LemonSqueezy, Search Console).
- You want method+path enforcement that prevents wrapper logic bugs from issuing write requests against the upstream API.
- You need a Google service-account JWT exchange path that goes through the same allowlist gate as data calls (no escape hatches).

**Do not use when**
- The MCP service exposes write tools — use @growth-labs/mcp-server directly. This scaffold is read-only by construction.
- The wrapper is the authority Worker itself (e.g. agent-auth.fulcrum-labs.com) — that calls api.cloudflare.com directly via global fetch and has no ctx.fetch model.
- You need a stateful auth resolver chain — use @growth-labs/mcp-auth's createCompositeResolver.

**Minimal setup**
- Install @growth-labs/mcp-wrapper-scaffold
- Define your wrapper's AllowEntry[]: per-(origin, method, pathPattern) entries for every upstream endpoint the wrapper hits (including the OAuth token-exchange endpoint if SA auth is in use)
- Define your wrapper's ToolDef[] using ctx.fetch (NOT global fetch) for every upstream call
- Call createWrapperServer({ tools, agentTokenBinding: env.AGENT_TOKEN, allowlist, metricsBinding: env.MCP_METRICS }) from your Worker's default export
- Add the monorepo lint rule that forbids global fetch in wrapper sources (per platform-foundations spec §4.4)

**Required bindings**
- `AGENT_TOKEN: SecretsStoreSecret bound to the shared agent bearer token`
- `Per-wrapper upstream credential binding (e.g. GA4_SA_JSON, LS_API_KEY) declared in the wrapper's Env extends BaseEnv`
- `Optional: MCP_METRICS: AnalyticsEngineDataset for per-tool-call metrics`

**Required env**
- `Optional (gateway-JWT dual-accept): AGENT_JWT_PUBLIC_KEYS — plain var, JSON string mapping kid → Ed25519 SPKI PEM (public keys are not secrets; pass current + previous during rotation)`
- `Optional (gateway-JWT dual-accept): AGENT_JWT_AUDIENCE — plain var, the wrapper's own trust domain (e.g. fulcrum-mcp-read). Both vars absent → legacy shared-bearer only, unchanged behavior`

**Working example:** `packages/mcp-wrapper-scaffold/README.md`

**Common mistakes**
- Calling global fetch() from wrapper source — must use ctx.fetch (closure pre-bound to the allowlist). The monorepo lint rule and §4.4 bundle-grep CI gate catch this.
- Omitting the OAuth token-exchange origin from the allowlist when using getGoogleAccessToken — the helper goes through ctx.fetch like everything else; missing the entry causes a synchronous throw.
- Treating the scaffold as a stateful service framework — it has no audit / authz / rate-limit primitives. Use @growth-labs/mcp-server for those.

**Related packages**
- `mcp-auth`
- `mcp-server`

## Go-plane capabilities (fulcrum-labs/foundry)

Every automated, scheduled, cross-site or media capability lives here. Before adding one, check the registered capabilities and the packages that already exist.

### `acquire.local_archive_discovery`

**Stage:** `acquire`
**Summary:** Observes a local archive drop against an expected-parts manifest and reports present/missing parts, so a delivery that is present but undiscovered fails loudly instead of reading as absent.
**Invocation:** Dispatch carrying the discovery manifest as a named artifact input; the runner's local paths and prior observations are runner configuration, never dispatch input. See capabilityplane/discovery.go.
**Hosts:** `hermes`

**Use when**
- A campaign expects archive parts to land on a runner's local disk and something must assert whether they actually did.
- A part-discovery result must be signed evidence rather than a log line.

**Do not use when**
- The source is an HTTPS URL: that is ingest.https.verified.
- You want to move or transform the archive; this capability only observes.

**Working example:** `capabilityplane/discovery_test.go`

### `audio.transcode.podcast`

**Stage:** `produce`
**Summary:** Transcodes one verified source into the registered podcast audio profile (mp3, 128 kbps, 44.1 kHz, mono) and returns only identity read back from the artifact store.
**Invocation:** Bundle dispatch with the source as a named artifact input; output identity is re-read from the store, never trusted from the terminal.
**Hosts:** `forge-executor`, `hermes`

**Use when**
- A published episode needs the estate's standard podcast audio rendition.

**Do not use when**
- You need video: that is encode.h264.quality-vbr or encode.av1.quality-vbr.
- You need a different audio profile; the profile is pinned in the host record and a dispatch cannot vary it.

**Working example:** `capabilityplane/audio_forge_test.go`

### `cut.ffmpeg.segment-remove`

**Stage:** `produce`
**Summary:** Removes keyframe-aligned time ranges from a source with an ffmpeg concat-demuxer stream copy -- no re-encode, CPU only. The de-sponsor cut leg.
**Invocation:** Dispatch with the source as the "source" named input and the ranges as the "cut-ranges" named input. Ranges never travel in SettingsEnvelope, which must stay byte-identical to the host registration.
**Hosts:** `hermes`

**Use when**
- Spans must be removed from a master without re-encoding it, and desponsor has already keyframe-aligned them.

**Do not use when**
- The ranges are not keyframe-aligned; align them with desponsor.SnapToSegments first or the copy will drift.
- You are deciding what to cut: that is the desponsor package, not this capability.

**Working example:** `capabilityplane/cut_test.go`

### `encode.av1.quality-vbr`

**Stage:** `produce`
**Summary:** AV1 NVENC quality-VBR encode on Forge's RTX 4080 SUPER, as a four-rung ladder (1080/720/480/360) or the single-clip legacy Reels rendition.
**Invocation:** Bundle dispatch for the ladder, artifact-render dispatch for the single rendition; the per-render window travels as the "selected-clip" named input.
**Hosts:** `forge-executor`

**Use when**
- A rendition set should be AV1 and the work can be pinned to Forge.

**Do not use when**
- The output must play everywhere today: h264 is the compatibility ladder.
- Forge is the wrong host for the job's locality; encode.h264.quality-vbr is registered on both hosts.

**Working example:** `cmd/foundry-capability-probe/main.go`

### `encode.h264.quality-vbr`

**Stage:** `produce`
**Summary:** H.264 quality-VBR encode as a four-rung ladder (1080/720/480/360) or the single-clip legacy Reels rendition. One capability ID, two host implementations -- Hermes VideoToolbox and Forge NVENC -- distinguished only by Version, with matching rungs so a request is host-agnostic.
**Invocation:** Bundle dispatch for the ladder, artifact-render dispatch for the single rendition. Registry.Select picks the host by operator preference, sole eligibility, or least in-flight jobs; SelectionReason records which.
**Hosts:** `forge-executor`, `hermes`

**Use when**
- A master needs the estate's standard multi-rendition h264 ladder.
- Either media host may serve the work and load should decide.

**Do not use when**
- You want to pin an encoder's bitrate ceiling by hand: the ladder's args are pinned in the host record (VideoToolbox is bitrate-laddered with qmin/qmax, never -maxrate).
- The job is audio only: that is audio.transcode.podcast.

**Working example:** `cmd/foundry-capability-probe/main.go`

### `encode.hls.ladder`

**Stage:** `produce`
**Summary:** Source-aspect long-form HLS: H.264/AAC VOD on the 360/480/720/1080 height ladder capped at the source (never upscaled), six-second aligned fMP4 segments from ffmpeg's hls muxer with explicit keyframe control, WebVTT captions and chapters as subtitle playlists, encoder-versions.json, and one canonical foundry.hls-inventory.v1 document whose sha256 is the receipt's commitment to every member. Master and rendition declarations (CODECS, RESOLUTION, FRAME-RATE, BANDWIDTH, AVERAGE-BANDWIDTH) are derived from the probed output, never ported.
**Invocation:** Artifact dispatch with the source as the "source" named input and optional "captions" / "chapters" (WebVTT on the source timeline) and "window" ({startMs,endMs}) inputs; Output is the inventory object, and every member is published under Output + "/gen-<digest>/" before the inventory lands last. Hermes runs the KB-pinned VideoToolbox ladder, Forge the NVENC ladder; the request is host-agnostic. See capabilityplane/hls.go.
**Hosts:** `forge-executor`, `hermes`

**Use when**
- A long-form master (channel video, Fronts editorial) needs the estate's adaptive HLS bundle for a site player.
- A consumer needs one verifiable document naming every playlist, segment and subtitle member with its content type, bytes and sha256 (W1-02 composition, W1-03 delivery, the authority's verification via VerifyHLSInventory).

**Do not use when**
- The output is a portrait social clip with burned-in karaoke captions: that is encode.h264.quality-vbr / encode.av1.quality-vbr, whose contracts stay under their own versions.
- The source is below 360 lines or has no video track; the capability refuses it as hls_source_unsupported rather than upscaling.
- You want to pick rungs by hand: the ladder is the registered profile capped at the probed source height, and the inventory records which rungs were omitted and why.

**Working example:** `capabilityplane/hls_test.go`

**Stage:** `acquire`
**Summary:** Fetches one HTTPS source into the artifact store with a bounded read and a SHA-256 identity verified on the way in.

**Hosts:** `forge-executor`, `hermes`

**Use when**

**Do not use when**

- The source is a local archive drop: that is acquire.local_archive_discovery.

**Working example:** `capabilityplane/ingest_probe_test.go`

**Stage:** `analyze`
**Summary:** One LLM chat completion with per-role route configuration, optional images, and output_json schema validation, executed in foundryd's own process rather than dispatched to an external runner.
**Invocation:** Dispatch with the request JSON as the "request" named input, bounded at 2 MiB. Spend is guarded by the capabilityplane binding, not by the llmchat protocol package.

### `maintenance.pf-cli.v1`

**Stage:** `produce`
**Summary:** Runs one pinned platform-foundations CLI (propagate, the conventions/dependency merge drivers, gh-settings sync) as a child process behind a versioned JSON contract -- CLI name, args, env variable NAMES (never values), and the git revision it must verify itself against before running anything. WH-05b's maintenance control loop: same TypeScript, a runner-executed launcher instead of a GitHub Actions job.
**Invocation:** Dispatch carrying the contract as a named "contract" artifact input, bounded at 16 KiB. Environment values are never dispatch input -- the runner resolves each declared name from the job's claim-time lease secrets first and its own configured secret handoff second, so a dispatch can never smuggle an arbitrary value. Runner-side requirements, not CLI env names: the claim must carry PF_REPO_FETCH_TOKEN (the authority-minted contents:read credential the runner fetches the pinned revision with; a claim without it fails the run loud before anything is fetched, and a contract that declares it as a CLI env name is refused), and the host must carry git and pnpm on PATH -- every run installs the pinned revision's lockfile (pnpm install --frozen-lockfile, CI=1) before the first CLI invocation, captured in the receipt and never skipped. See capabilityplane/maintenancepfcli.go.
**Hosts:** `colossus-ci`

**Use when**
- A DBOS schedule needs to run a pinned external CLI on an enrolled runner and get a signed receipt back (exit code, duration, captured stdout/stderr, the revision actually checked out) rather than trusting a GitHub Actions run's own conclusion.

**Do not use when**
- The work is a Go-native capability: this is specifically for shelling to an existing external CLI/language runtime behind a pin, not a substitute for writing the logic in Go.
- You need a general-purpose shell job with fleet-wide secrets: this capability's contract carries env NAMES only, resolved through the runner's own narrow secret handoff, never an ambient credential.

**Working example:** `capabilityplane/maintenancepfcli_test.go`

## Established approaches

### Identity, sessions, sign-in

One OpenAuth issuer per organisation (identity-platform, `auth.fulcrum-labs.com` for Fulcrum Labs) consumed through `@growth-labs/auth` on Workers and `packages-go/auth` in Go. Never scaffold a standalone auth path, per-site user store or hand-rolled password flow.

**Pointer:** KB `openauth-single-issuer`; `growth-labs/identity-platform`

### Secret placement

Shared multi-consumer values → account Secrets Store bindings; unique single-Worker values → per-Worker secrets; service identity → minted EdDSA JWTs or service bindings; non-secret config → `[vars]`; Go services → 0600 files under `/etc/<service>/secrets/` with Vaultwarden pointers. Files and docs carry pointers, never values.

**Pointer:** KB `cloudflare-secret-homes-doctrine-2026-07-15`

### UI — Astro sites

StarwindUI Pro is the component system: owned source under `components/starwind/`, extended in place. Check https://starwind.dev/llms-full.txt before creating a custom component; the `no-custom-components` hook nudges on creation.

**Pointer:** platform-foundations `platform/ui.md`

### UI — React/SPA apps

No shared component or tokens package exists yet. `fulcrum-labs/fulcrum-projects` vendors the Growth Labs design tokens (`gl-*.css`) from `fulcrum-labs-web` by copy and keeps its own component set. A `@growth-labs/tokens` package is the decided home (spec `growth-labs-tokens-package`); until it ships, re-vendor the tokens from `fulcrum-labs-web` rather than inventing new ones.

**Pointer:** olympus-control-plane `docs/specs/shared-capability-doctrine.spec.md`, Decision 3

### Legacy Cloudflare Foundry registry

The TypeScript Foundry on Cloudflare (`fulcrum-labs/the-foundry`) is frozen. Its ~55 registered capabilities are discovered live with the `capabilities_list` and `capability_describe` MCP tools and are never enumerated here; new automated capabilities are built on the Go plane.

**Pointer:** KB `go-services-hosted-on-atlas-until-new-machine-2026-09-04`; olympus `docs/specs/lane-go-foundry-plane.spec.md`
